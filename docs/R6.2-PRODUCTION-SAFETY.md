# R6.2 — Production Safety & Conditional Loading

Status: COMPLETE

## Goal

Make Runtime Intelligence safe to keep available in an application without silently paying runtime cost when diagnostics are disabled.

The product remains explicitly opt-in. Production builds that want the strongest isolation should import only `runtime-intelligence/loader` from always-loaded code and dynamically load the framework/panel modules after their own development/debug gate evaluates to `true`.

## Production-safe loading boundary

New public entry:

```js
import { loadRuntimeIntelligence } from 'runtime-intelligence/loader';

const loaded = await loadRuntimeIntelligence({
  enabled: import.meta.env.DEV && debugEnabled,
  framework: 'react',
  panel: true,
});

if (loaded.enabled) {
  // loaded.frameworkModule is runtime-intelligence/react
  // loaded.panelModule is runtime-intelligence/panel
}
```

The loader:

- is disabled by default;
- accepts only literal `true` as enabled, so configuration fails closed;
- has no static import of core, React, Lit or panel code;
- imports only the selected framework and optionally the panel;
- provides a deliberate code-splitting boundary without claiming that every legacy module is side-effect-free.

R6.2 intentionally does **not** set package-level `sideEffects: false`. Some mature/legacy UI modules still perform registration when explicitly imported. The `/loader` boundary is the safe Pareto contract until those internals are separately normalized.

## Disabled framework paths

`RuntimeIntelligenceProvider enabled={false}` no longer constructs `ReactIntelligenceRuntime` just because the provider rendered. Runtime creation is lazy and happens only after enablement; Profiler wrapping and browser services remain absent while disabled.

`LitDebugMixin` now checks the Runtime Intelligence gate before connecting the Lit adapter or baseline collectors. With no master/per-tool debug flag enabled, component lifecycle/update hooks pass directly through to the host component.

## Reversible browser instrumentation

A started browser runtime owns three global instrumentation leases:

- network interception (`fetch` / XHR);
- console capture;
- PerformanceObserver-based vitals.

They are now released when the browser runtime stops:

- original `fetch`, XHR `open` and XHR `send` functions are restored;
- original `console.error` and `console.warn` function identities are restored;
- vitals observers are disconnected;
- browser error / rejection / interaction listeners are removed;
- the temporary `__LDS_INTELLIGENCE_ENABLED__` flag is restored to its previous host value or removed;
- diagnostics globals owned by the stopped collector are removed.

Network/console/vitals use lightweight client counts so one diagnostics consumer cannot tear down instrumentation still owned by another consumer.

Restoration is defensive: a Runtime Intelligence teardown only replaces a global method when that method is still the wrapper Runtime Intelligence installed. If another library patched it later, Runtime Intelligence does not overwrite that newer patch.

## No surprise network calls

Runtime Intelligence's network layer observes host `fetch`/XHR traffic; initializing the observer does not initiate a request of its own.

Production-safety tests verify that network initialization changes the interceptors without calling the original `fetch`, and that detach restores the host functions.

Runtime Intelligence does not add telemetry/upload behavior in this mission. JSON/HTML export remains local/user-triggered.

## Validation

Focused production-safety coverage now checks:

- disabled conditional loading invokes zero framework/panel loaders;
- enabled loading imports only the selected surfaces;
- network interception is reversible and makes no request during initialization;
- console import is inert and attach/detach restores exact host methods;
- vitals observers disconnect on teardown;
- BrowserRuntimeSurface releases collector leases/listeners and restores the intelligence flag;
- Lit instrumentation stays gated while disabled;
- React runtime construction stays behind the `enabled` branch.

Run:

```bash
npm run production:validate
npm run package:validate
npm test
```

During implementation, the standalone R6.2 production-safety test file was executed locally against the changed modules: **8 passed, 0 failed**. A complete checked-out repository test run is still required in a normal repository environment before release; connector work does not claim that full suite as executed.
