# R6.5 — Distribution / License / IP Strategy

Status: COMPLETE

## Decision

Runtime Intelligence adopts a **private/proprietary distribution baseline** for the R6 product.

The browser package remains fully functional as a local developer product, but source/package access is controlled. Public npm publication and an open-source license are not part of the current product strategy.

## Package identity

The package remains named:

```text
runtime-intelligence
```

This is the stable internal package-contract name used by the R6 APIs and documentation.

R6.5 deliberately does not rename it to a guessed npm/GitHub Packages scope. A future private registry may require a scoped registry package name, but that is a distribution mapping problem rather than an architecture change. Avoid breaking imports until an actual registry/namespace exists.

## License position

`package.json` now uses:

```json
"license": "UNLICENSED"
```

and the repository includes `LICENSE.md` with the proprietary/all-rights-reserved notice.

This is the policy for current and future R6.5 distributions. It does not attempt to rewrite history or revoke rights that may already have been granted by an earlier distribution or separate agreement. Obtain legal review before external commercial licensing or relying on historical-license conclusions.

Third-party dependencies keep their own licenses.

## Distribution channels

### Approved now

1. **Authorized private Git access**, preferably pinned to an explicit commit SHA for consumers.
2. **Authorized tarball delivery**, produced with `npm pack`, for reproducible installation/testing.

Both channels provide inspectable JavaScript/source to an authorized consumer. That is acceptable for the current product model; the license and access controls define usage rights.

### Not approved in R6

- public npm publication;
- public GitHub release artifacts intended for unrestricted redistribution;
- CDN/browser delivery as a public script;
- changing `private: true`;
- changing `UNLICENSED` to an open-source license without an explicit owner decision.

No npm registry is hard-coded. If a private registry is later selected, its account/scope/access policy should be configured deliberately.

## Why not rely on obfuscation

Browser JavaScript cannot be made meaningfully secret once delivered to a client.

Minification, bundling and obfuscation may increase copying/debugging effort, but they are not a security or IP boundary. Do not distort the architecture to create the appearance of secrecy.

Use normal production bundling for size/performance. Use access controls, license terms and—where secrecy is actually required—a service boundary.

## Product/IP boundary

### Keep in the browser package

These need to run close to the application and should remain local-first:

- framework adapters and lifecycle integration;
- browser/runtime collectors;
- UREP evidence protocol and evidence store;
- EvidenceGraph/root-cause primitives;
- privacy/redaction;
- canonical local panel;
- normalized JSON/HTML reporting;
- local advisers/opportunities that do not require secret server-side assets;
- extension contract.

The product must remain useful without a network service.

### Candidates for a future proprietary service boundary

Move something server-side only when server-side operation creates real product/IP value, for example:

- proprietary ranking/scoring models that should not ship to browsers;
- organization-wide cross-session aggregation;
- commercial rules/policies or continuously updated intelligence packs;
- fleet-wide regression learning;
- hosted source/repository correlation requiring protected credentials;
- premium AI synthesis over sanitized evidence;
- entitlement/licensing services.

A future service should consume a documented, sanitized contract (for example normalized reports/evidence capsules) and return advisory results. It must be **opt-in**, explicitly configured and separate from local collection. R6.5 does not add any automatic telemetry or backend calls.

## Version/release mechanics

Current package version remains `0.1.0`.

Versioning follows the R6.4 API policy:

- before 1.0, a breaking supported-public-API change increments the minor line;
- compatible changes increment patch;
- after 1.0, semantic-versioning major/minor/patch rules apply;
- UREP and extension compatibility remain same-major.

For controlled consumer baselines, pin an exact Git SHA or exact tarball/version. Do not use floating `main` installs for validation baselines.

## Machine-enforced policy

Run:

```bash
npm run distribution:validate
```

The validator requires:

- `private: true`;
- `license: "UNLICENSED"`;
- no public `publishConfig`;
- no hard-coded registry;
- no automatic publish lifecycle script;
- proprietary/all-rights-reserved `LICENSE.md`;
- R6.5 policy and README distribution wording;
- `LICENSE.md` and `README.md` included in the packed artifact.

`npm run validate:release` includes this policy check.

## TrustWeave

TrustWeave stays on the validated R5.7.4 SHA until a deliberate R6 dogfood adoption mission. R6.5 does not repin it and does not change its installation path.

## R6 closure

R6.1–R6.5 now provide:

1. package contract and pack safety;
2. production-safe conditional loading;
3. reproducible onboarding/install;
4. stable public API + governed extension contract;
5. distribution/license/IP policy.

The productization baseline is therefore complete.
