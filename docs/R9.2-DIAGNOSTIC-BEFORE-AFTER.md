# R9.2 — Diagnostic Before/After Experience

> **R9.3 semantic hardening:** the original R9.2 implementation captured cumulative EvidenceStore snapshots for baseline and replay. R9.3 supersedes that behavior with isolated evidence sequence windows: create/start the session before reproducing the baseline; baseline capture closes the first window; replay capture includes only later evidence. See [R9.3-FINDING-VERIFY-FIX-BRIDGE.md](R9.3-FINDING-VERIFY-FIX-BRIDGE.md).

## Status

IMPLEMENTED in source and subsequently hardened by R9.3. The mission turns the existing workflow baseline/compare/verify primitives into one bounded developer flow without changing R9.1 causality semantics.

## Developer flow

```text
start diagnostic session
  → reproduce problem
  → capture baseline
  → apply intended fix
  → replay the same workflow
  → capture replay
  → improved / unchanged / regressed / inconclusive
```

The experience is framework-neutral and reads from the same shared UREP `EvidenceStore` used by React, Vue and Lit. Starting the session before the baseline workflow is important because R9.3 uses that moment as the beginning of the baseline evidence window.

## Public API

`runtime-intelligence/panel` now exports:

- `DiagnosticBeforeAfterStatus`
- `createDiagnosticBeforeAfterSession(...)`

The canonical panel mount also exposes:

- `startBeforeAfter(...)`
- `getBeforeAfterState()`

Example:

```js
import { MetricDirection } from 'runtime-intelligence/core';

const session = panel.startBeforeAfter({
  workflowId: 'save-product',
  target: {
    metricId: 'count:error',
    direction: MetricDirection.DECREASE,
  },
  intervention: {
    id: 'fix-save-race',
    description: 'dedupe duplicate save request',
    applied: true,
  },
});

// Reproduce the problem AFTER the session starts.
// Then close the baseline evidence window.
session.captureBaseline();

// Apply the intended fix, replay the same workflow, then close the replay window.
session.captureReplay();

console.log(session.getState());
```

Custom workflow metrics supported by `createWorkflowRun(...)` can be supplied through the `metrics` option.

## Status semantics

### `awaiting-baseline`

The session has started and marked the current latest evidence sequence. Reproduce the target workflow; only later evidence enters the baseline window.

### `awaiting-replay`

The baseline exists. Apply the intended fix, replay the same workflow and capture the replay. Only evidence emitted after baseline capture enters the replay window.

### `improved`

The configured verification target met its threshold.

This does **not** automatically mean the intervention caused the improvement. Without separate governed causal evidence the underlying verification remains:

- `verificationConfirmed: true`
- `causalityConfirmed: false`
- `evidenceLevel: correlation`

### `unchanged`

The replay did not meet the configured improvement threshold. This includes zero change and positive movement that remains below the declared threshold.

### `regressed`

The target moved in the wrong direction.

### `inconclusive`

The comparison cannot support a useful conclusion, for example because the intervention was not confirmed applied, the target metric is unavailable or the workflow/run identity is invalid.

## Evidence windows

R9.3 adds explicit state metadata:

```js
state.windows = {
  baselineStartSequence,
  replayStartSequence,
};
```

The store is not cleared. Historical/runtime evidence remains available to the rest of Runtime Intelligence while the diagnostic workflow consumes only its own bounded before/after windows.

This correction is important for count-based metrics: baseline events are no longer counted again during replay merely because the shared store is cumulative.

## Reporting

When a session is started through the canonical panel mount, `createReport()` attaches the current state as `diagnosticBeforeAfter`.

JSON exports therefore preserve:

- workflow/target/intervention metadata;
- baseline/replay sequence-window boundaries;
- bounded baseline and replay workflow snapshots;
- target before/after values;
- improvement and relative improvement;
- verification outcome/evidence level;
- explicit causality flag;
- developer-facing headline, next action and evidence note.

HTML reports render a dedicated **Diagnostic before / after** section with the same evidence boundary.

The existing report privacy sanitizer still applies to the complete export. No raw runtime payload boundary is widened.

## Compatibility

The mission remains additive:

- no existing public export was removed or renamed;
- no UREP schema version change;
- no framework adapter change;
- no telemetry/background upload;
- no TrustWeave changes;
- no Angular work.

R9.3 adds sequence-window state and the Finding → Verify Fix bridge without changing R9.1 causality semantics.

## Validation scope

Focused unit coverage now includes:

- baseline/replay guided state transitions;
- historical evidence excluded from the baseline window;
- baseline evidence excluded from a cumulative replay snapshot;
- meaningful improvement remaining correlation-level under R9.1;
- unchanged/below-threshold result;
- regression;
- inconclusive result;
- replay-before-baseline guard;
- reset beginning a fresh sequence window;
- immutable/JSON-safe state;
- JSON report inclusion;
- HTML report rendering with explicit `causality not confirmed` wording.

The full repository release gate must be rerun in a normal checked-out development environment before treating R9.2/R9.3 as fully release-validated.

## Boundaries

R9.2/R9.3 are not an experiment platform and do not add statistical causal inference. They make existing diagnostic verification easier to use and interpret.

TrustWeave remains parked. R10 Angular remains deferred.
