# R9.4A — Comparative Value Proof Pilot

## Status

**IMPLEMENTED — PROTOCOL/HARNESS READY; HUMAN PILOT RESULTS PENDING.**

R9.4A freezes broad product expansion and turns the R9.3 strategic question into a falsifiable pilot:

```text
native tooling only
vs
Runtime Intelligence Level 0
vs
Runtime Intelligence targeted instrumentation
```

No runtime analyzer, framework adapter, panel feature or evidence claim is added by this mission.

## Why this mission exists

Runtime Intelligence already has substantial architecture. The unresolved question is product value:

> Does the product get an experienced engineer to a trustworthy source, diagnosis/action and verification outcome materially better than the native tools they already know?

The benchmark is designed so Runtime Intelligence is allowed to lose.

## Delivered

### 1. Frozen nine-fault corpus

`benchmarks/value-proof/faults.json` defines nine real-behavior scenarios:

- 3 React;
- 3 Vue;
- 3 Lit;
- 3 source/provenance cases;
- 3 cross-signal cases;
- 3 action/verification cases.

The corpus uses existing behavioral lab scenarios rather than injected coverage.

### 2. Anti-confirmation-bias balance

`benchmarks/value-proof/oracles.json` classifies the hidden adjudication set as:

- 3 analyzer-favorable;
- 3 neutral;
- 3 known-limit.

The oracle is read only after all three modes for a fault are completed.

Known-limit cases are intentional. A product that honestly says “I cannot prove this at Level 0” can score better on trust than one that invents a confident diagnosis.

### 3. Counterbalanced run order

Every fault runs all three modes, but the first mode is balanced:

- native first: 3;
- RI Level 0 first: 3;
- RI targeted first: 3.

This does not turn a one-participant pilot into a controlled experiment, but it avoids always giving the same mode the learning advantage.

### 4. Human-only timing contract

The committed template contains no timings and no result rows.

Timing must be recorded by a human during the run. Missing milestones stay `null` with a reason.

The harness does not generate or infer developer-time savings.

### 5. Trust/noise/instrumentation measures

Each result records:

- relevant-source outcome;
- diagnosis outcome;
- action specificity;
- verification usefulness;
- findings shown/useful/irrelevant/false-positive;
- instrumentation files/lines changed;
- developer reuse choice;
- explicit trust violations.

Trust violations include false exact source, generated-as-original source, correlation-as-causality and unsupported ownership-as-proof.

### 6. Machine-checkable study contract

`npm run value-proof:validate` verifies:

- exactly nine faults;
- 3/3/3 framework balance;
- 3/3/3 value-category balance;
- three unique run modes per fault;
- first-run counterbalancing;
- 3/3/3 favorable/neutral/known-limit oracle balance;
- declared lab/source files exist;
- no precommitted results;
- no expected winner/time-saved field in the frozen manifest.

The validator passing means only that the protocol is internally consistent. It is not value proof.

### 7. Honest result summarizer

`npm run value-proof:summarize -- <results.json>` requires a complete 27-run one-participant pilot and reports:

- useful source/diagnosis/action counts by mode;
- source/diagnosis milestone reach counts;
- medians only from actual human timings;
- irrelevant/false-positive finding totals;
- trust violations;
- instrumentation cost;
- “would use again” counts.

It deliberately does not auto-declare a winner.

## Evidence-honesty requirements

The benchmark preserves the same product contract:

```text
observation ≠ causality
correlation ≠ causality
source attribution ≠ business root cause
structural ownership ≠ causal ownership
verification improvement ≠ causal proof
```

A wrong confident answer is worse than an explicit unavailable/unsupported result.

## What this mission does not prove

R9.4A uses repository fault labs for reproducibility. Some scenarios overlap current product capabilities.

Therefore:

- it is not an external customer study;
- it is not a two-developer controlled A/B trial;
- it is not evidence of market demand;
- it cannot establish general developer-time savings;
- it does not replace real-consumer validation.

A promising pilot should lead to independent/non-lab validation, not feature expansion.

## Decision gate

After real pilot data exists:

### Continue / R9.4B candidate

Continue only if the evidence shows repeated concrete value on difficult cases and trust remains intact. Fix only defects exposed by the pilot.

### Narrow / simplify

Narrow the product if native tooling wins most cases, RI mainly adds another panel, or targeted instrumentation cost erases its diagnostic advantage.

### Stop broad expansion

Any recurring evidence overclaim, wrong-source confidence, or pervasive false positives blocks expansion regardless of speed.

Angular remains deferred.

