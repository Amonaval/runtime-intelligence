# R6.4 — Public API Stability & Extension Contract

Status: COMPLETE

## Goal

Freeze the R6 consumer-facing contract before broader distribution, while keeping internal implementation freedom.

R6.4 does four things:

1. defines the supported package/API surface;
2. makes accidental public-API drift testable;
3. introduces one governed extension path for custom evidence producers;
4. explicitly removes `window.__LDS_*` and deep source imports from the supported consumer contract.

## Public vs internal

Supported package subpaths:

- `runtime-intelligence/loader`
- `runtime-intelligence/core`
- `runtime-intelligence/extension`
- `runtime-intelligence/react`
- `runtime-intelligence/lit`
- `runtime-intelligence/panel`
- `runtime-intelligence/panel/lit`

Only named exports exposed by those subpaths are part of the R6.4 public baseline.

Not public:

- `runtime-intelligence/lit/src/...` or any other deep repository path;
- `lit/custom/*`;
- `lit/src/integration/*`;
- `lit/src/archive/*` and `lit/src/future/*`;
- private methods/fields on the mature panel element;
- `window.__LDS_*` browser globals.

Some browser globals still exist as internal compatibility bridges for the mature panel/legacy tooling. They may change without public-API compatibility guarantees. Consumers should use package APIs, runtime/store references, panel mount APIs, and the extension contract instead.

## API compatibility baseline

`RUNTIME_INTELLIGENCE_API_VERSION` is `0.1`.

Compatibility policy:

- while package API is pre-1.0, a breaking supported-API change requires a new package minor line (`0.1` -> `0.2`);
- after 1.0, breaking changes require a major version;
- additive compatible changes may be made within the current line only after the public API baseline is deliberately updated;
- UREP compatibility is same-major;
- extension API compatibility is same-major;
- deep imports and browser globals have no compatibility guarantee.

`npm run api:validate` compares the current package subpaths and named exports against `scripts/public-api-baseline.json`. A future mission cannot silently rename/remove/add supported exports without explicitly updating that baseline and its compatibility documentation.

## Extension API

New public surface:

```js
import { createRuntimeExtension } from 'runtime-intelligence/extension';
```

Extensions must receive an explicit EvidenceStore-compatible store. They do not discover a store through browser globals.

Example:

```js
const extension = createRuntimeExtension({
  id: 'acme.router',
  version: '1.0.0',
  store: runtime.store,
  framework: 'react',
});

extension.diagnostic('cache-miss', {
  route: '/orders',
});
```

The emitted diagnostic is automatically namespaced as:

```text
acme.router.cache-miss
```

Every emitted event receives immutable extension manifest metadata under `payload.extension`:

```js
{
  id,
  version,
  extensionApiVersion,
  urepSchemaVersion
}
```

The extension surface intentionally emits only existing UREP event types. R6.4 does not create an ungoverned arbitrary event namespace beside UREP.

## Evidence honesty for extensions

Extensions default to observation-level/unknown-attribution evidence unless they explicitly provide stronger supported evidence metadata.

The strongest causal field is guarded:

- `causedByEventId` is rejected by default;
- `causality-confirmed` is rejected by default;
- an extension must set `allowConfirmedCausality: true`;
- it must also emit `evidence.level = 'causality-confirmed'`;
- and it must supply `correlation.causedByEventId`.

This does not make the claim true by itself. It only prevents casual/accidental promotion of temporal correlation into causality. Extension authors remain responsible for deterministic proof, and the underlying EvidenceStore still validates protocol/reference integrity.

## Extension compatibility

The extension manifest records both:

- `extensionApiVersion` — currently `1.0`;
- `urepSchemaVersion` — currently the active UREP schema.

`isRuntimeExtensionCompatible()` and `assertRuntimeExtensionCompatibility()` use same-major compatibility for both contracts.

A future incompatible extension API or UREP major must fail explicitly instead of being silently accepted.

## Scoped extension access

A runtime extension exposes:

- `emit(input)` — governed UREP emission;
- `diagnostic(name, payload, options)` — namespaced diagnostic helper;
- `snapshot(filter)` — returns evidence emitted by that extension only;
- `subscribe(fn)` — receives evidence emitted by that extension only;
- `describe()` — manifest/framework/causality policy.

This avoids giving ordinary plugins a reason to depend on incidental panel globals.

## Automated contract checks

New command:

```bash
npm run api:validate
```

It validates:

- exact supported package subpaths;
- exact named-export baseline for every public subpath;
- API version alignment with the baseline.

`npm run package:validate` now also checks `types` targets, not only runtime import targets.

`npm run onboarding:validate` now smoke-imports `/extension` from the packed tarball and emits a real namespaced diagnostic through a fresh `EvidenceStore`.

`npm run validate:release` includes API validation.
