# R9.3 — Finding → Verify Fix Bridge

## Status

IMPLEMENTED IN SOURCE.

R9.3 connects selected normalized findings to the R9.2 diagnostic before/after workflow while preserving the R9.1 evidence/causality contract.

It also closes the previously missing Lit fault-lab gap and adds a single minimal-to-full developer guide for React, Vue and Lit.

## Problem

R9.2 made baseline/replay verification usable, but the developer still had to manually choose a workflow id, metric and target.

That left a gap:

```text
Runtime Intelligence finding
→ developer understands it
→ developer fixes code
→ ? how do I configure verification?
```

R9.3 adds a bounded bridge:

```text
supported finding
→ honest derived verification plan
→ start session before baseline reproduction
→ capture baseline
→ apply fix
→ replay
→ capture replay
→ improved / unchanged / regressed / inconclusive
```

## Public API

`runtime-intelligence/panel` now exports:

- `FindingVerificationSupport`
- `createFindingVerificationPlan(finding)`
- `createFindingVerificationSession(...)`

The canonical panel mount adds:

- `panel.startFindingVerification(finding, options)`

Starting through the panel switches to the existing Before/After experience.

## Automatic mappings

Automatic targets are intentionally narrow.

### Runtime error

`runtime-error` derives an owner-scoped custom error-count metric and a decrease target.

### Update storm / update-budget opportunity

`render-storm` and `update-budget-opportunity` derive an owner-scoped completed-update count and a decrease target.

### Slow render

`slow-render` is supported only if the finding actually carries a numeric render duration field:

- `actualDurationMs`, or
- `durationMs`.

The bridge reuses the field actually observed; it does not guess one.

### Unsupported findings

Findings such as virtualization, paint, worker, sequential API and broad resource/memory opportunities do not receive an invented default metric.

The returned plan is explicitly unsupported with a reason. A developer can still create a manual before/after session by supplying a meaningful explicit workflow/target.

## R9.2 correctness hardening discovered during R9.3

The R9.2 session originally captured the complete cumulative EvidenceStore for both baseline and replay.

That was unsafe for count-based comparisons because baseline events could be counted again in the replay snapshot.

R9.3 changes the session to use sequence windows:

```text
session starts at sequence N
→ baseline includes only sequence > N
→ baseline captured at sequence M
→ replay includes only sequence > M
```

This preserves the EvidenceStore and avoids destructive clearing while isolating the two diagnostic workflows.

`reset()` begins a new baseline window at the latest sequence.

## Evidence semantics

R9.3 does not change R9.1:

```text
verified improvement ≠ confirmed causality
```

A normal successful finding verification remains:

- `verificationConfirmed: true`
- `causalityConfirmed: false`
- `evidenceLevel: correlation`

A causal upgrade still requires separate governed UREP `causality-confirmed` evidence.

## Lit Fault Lab

`examples/lit-fault-lab` is now the runnable full-scale Lit example.

It demonstrates:

- off-by-default opt-in;
- public Lit programmatic activation;
- one shared `LitDebugMixin(LitElement)` base;
- canonical panel/shared EvidenceStore;
- real runtime error and HTTP failure;
- sequential requests;
- slow render;
- update storm;
- large non-virtualized list;
- intentional retained listener challenge;
- Finding → Verify Fix;
- before/after report/export semantics.

Run:

```bash
npm run lab:lit:install
npm run lab:lit
```

## Scope boundaries

R9.3 does not add:

- statistical causal inference;
- Angular;
- new telemetry;
- TrustWeave work;
- automatic metrics for every finding;
- a new evidence schema.

The next strategic phase should prove value on realistic faults rather than expand feature/framework count.
