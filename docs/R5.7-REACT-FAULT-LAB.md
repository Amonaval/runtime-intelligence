# R5.7 — React Fault Lab + Validation Harness

## Goal

Validate React parity without contaminating TrustWeave or weakening evidence honesty.

A random public React sample app is intentionally not the primary harness: its behavior is uncontrolled, its defects are not deterministic, and a missing finding cannot tell us whether the product failed or the sample simply did not exercise the capability.

R5.7 adds a dedicated `examples/react-fault-lab` with two complementary validation layers.

## Layer 1 — behavioral faults

These are real runtime behaviors in an isolated React application:

- React Profiler slow render (~620 ms)
- rapid tracked-state updates / render storm
- unhandled promise rejection
- slow HTTP request
- HTTP error
- sequential HTTP calls
- large response followed by a main-thread long task
- duplicate dialog DOM
- large unvirtualized list
- tracked resource destroyed without release evidence

The faults are not exported by the package and do not exist in TrustWeave.

## Layer 2 — deterministic UREP injection

`injected-scenarios.js` emits explicitly labeled `fault-lab-injected` evidence for rare or browser-dependent paths. This validates the canonical bridge, mature panel and Intelligence pipeline without claiming the application was actually observed to have those defects.

Injected coverage includes slow render, state thrash, slow API, DOM duplication, virtualization, expensive paint, worker opportunity, sequential API opportunity, update budget, error and resource lifetime violation.

## Why both layers are required

- Synthetic evidence proves presentation/correlation plumbing but not detection.
- Real faults prove detection but cannot reliably cover every browser capability.
- TrustWeave remains pure real-world dogfood and contains no test-only defects.

## Cross-surface defects found while designing the lab

The validation design exposed two React parity mismatches and R5.7 fixes them:

1. `IdleSchedulingAdvisor` consumed only `payload.durationMs`, while React Profiler emits `actualDurationMs`. It now accepts both and prefers explicit `INTERACTION` evidence before the legacy `STATE_CHANGED` fallback.
2. `WorkerOpportunityAdvisor` expected network `responseSize` + `url`, while the shared browser surface publishes `responseSizeKB` + `path`. It now normalizes the supported payload aliases before correlation.

Regression tests cover both mismatches.

## Run

```bash
npm run lab:react:install
npm run lab:react
```

The lab opens the same canonical mature `LdsDebugPanel` used by React consumers.

## Acceptance

React capability is considered validated only when the behavioral case is detected where browser support permits it, deterministic UREP renders correctly, evidence wording remains honest, and no fixture code is required in TrustWeave.
