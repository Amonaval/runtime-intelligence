## Problem corrected

The original workflow verifier treated a successful before/after replay as `causality-confirmed` when an intervention was marked applied and the target metric improved beyond configured thresholds.

That exceeded Runtime Intelligence's current evidence-honesty contract. A temporal sequence:

```text
before
→ intervention
→ replay
→ metric improves
```

can verify that the target improved after the intervention, but it does not by itself prove that the intervention caused the improvement. Cache state, workload/data changes, nondeterminism, timing variance, unrelated changes and other confounders can remain.

R9.1 aligns workflow verification with the modern UREP/P0/R8/R9 semantics.

## Delivered

### 1. Replay improvement no longer invents causality

`verifyFix(...)` keeps the existing successful verification outcome/compatibility surface:

- `outcome: "confirmed"`
- `confirmed: true`

but these fields now mean that the configured verification target was met on a distinct replay of the same workflow after an explicitly applied intervention.

A normal successful replay now returns:

- `verificationConfirmed: true`
- `causalityConfirmed: false`
- `evidenceLevel: "correlation"`
- reason: `meaningful-improvement-verified-after-applied-intervention-without-causal-proof`

This preserves the existing public outcome while making its evidence meaning explicit.

### 2. Causal upgrade requires pre-existing governed UREP causal evidence

`verifyFix(...)` accepts an optional `causalEvidence` UREP event.

It does **not** derive causality from the before/after comparison. A causal upgrade is allowed only when the supplied event:

- is a valid current UREP evidence event;
- already carries `evidence.level = "causality-confirmed"`;
- carries `correlation.causedByEventId`.

When both meaningful workflow improvement and that stronger event are present, verification can return:

- `verificationConfirmed: true`
- `causalityConfirmed: true`
- `evidenceLevel: "causality-confirmed"`
- a bounded `causalEvidence` reference containing event id/type, caused-by id and framework.

This composes with the existing governed extension contract, which independently requires explicit opt-in before an extension can emit confirmed causality.

### 3. Non-success outcomes remain correlation-level

Workflow mismatch, same-run replay, intervention-not-confirmed, unavailable target metrics, below-threshold improvement and regression never gain causality from chronology alone.

They explicitly return:

- `verificationConfirmed: false`
- `causalityConfirmed: false`
- correlation-level evidence.

### 4. Evidence Capsule handoff language hardened

The Evidence Capsule AI prompt now distinguishes:

- verification outcome;
- whether causality is actually confirmed.

It instructs consumers not to promote correlation to causality unless the capsule carries governed `causality-confirmed` evidence.

No raw runtime payload/export privacy boundary was widened.

## Compatibility

No existing public function/export was removed or renamed.

`VerificationOutcome.CONFIRMED` and `confirmed` remain available for compatibility, but their meaning is now explicitly **verification confirmed**, not **causality confirmed**.

The additive fields are:

- `verificationConfirmed`
- `causalityConfirmed`
- `causalEvidence`

No UREP schema change, new framework adapter, telemetry, package distribution change or new public package surface was introduced.

## Boundaries

R9.1 does not add statistical causal inference, controlled-experiment orchestration or framework-specific causal logic.

A `causality-confirmed` event is still a strong claim and must originate from a producer that is entitled to make that claim under the UREP/extension contract. `verifyFix` merely consumes that stronger evidence; it does not manufacture it.
