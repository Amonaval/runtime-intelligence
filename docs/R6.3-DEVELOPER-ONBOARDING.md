# R6.3 — Developer Onboarding & Reproducible Installation

Status: COMPLETE

## Goal

Make Runtime Intelligence adoptable by another developer without repository archaeology, while preserving the R6.1/R6.2 safety decisions.

The R6.3 contract is:

1. a root README must get a React or Lit developer to first instrumentation in about five minutes;
2. the recommended pre-registry install path must validate the actual packed artifact;
3. development enablement must stay explicit and production-safe;
4. troubleshooting must distinguish packaging, activation, runtime, panel, and evidence issues;
5. report/export behavior must be clear and local by default.

## Installation modes

### A. Local tarball — recommended before registry publication

From the Runtime Intelligence repository:

```bash
npm pack --ignore-scripts
```

Then in the consumer application:

```bash
npm install /absolute/path/to/runtime-intelligence-0.1.0.tgz
```

Why this is the preferred R6.3 path:

- it exercises the exact `files` allowlist and `exports` map;
- it catches missing packed files that repository-relative imports can hide;
- it behaves much closer to a registry package than `npm install ../runtime-intelligence`;
- it does not require us to decide public/private registry or final licensing yet.

### B. Git SHA — existing dogfood compatibility

Existing dogfood may remain pinned to an explicit Git SHA. This is useful for validation baselines, but it is no longer the primary onboarding recommendation because a Git install can expose repository layout that will not exist in a packed artifact.

### C. Registry package — intentionally deferred

R6.3 does not publish the package. R6.5 owns the decision on package name, registry visibility, license/IP policy, and commercial/open-source boundary.

## React quick start

Use `runtime-intelligence/loader` in always-loaded application code.

```js
import { loadRuntimeIntelligence } from 'runtime-intelligence/loader';

const loaded = await loadRuntimeIntelligence({
  enabled: import.meta.env.DEV && debugToggle === true,
  framework: 'react',
  panel: true,
});
```

If disabled, render the app normally.

If enabled:

```js
const {
  createReactIntelligenceRuntime,
  RuntimeIntelligenceProvider,
} = loaded.frameworkModule;
const { mountRuntimeIntelligencePanel } = loaded.panelModule;

const runtime = createReactIntelligenceRuntime({ profilingEnabled: true });
const panel = mountRuntimeIntelligencePanel({ store: runtime.store });

root.render(
  <RuntimeIntelligenceProvider runtime={runtime}>
    <App />
  </RuntimeIntelligenceProvider>,
);
```

The provider owns component/profiler lifecycle. The panel consumes the same evidence store. For test/HMR teardown, call `panel.destroy()` and `runtime.stop()`.

## Lit quick start

Strict bundle-isolation mode must make the loading decision before instrumented classes are registered:

```js
import { LitElement } from 'lit';
import { loadRuntimeIntelligence } from 'runtime-intelligence/loader';

const loaded = await loadRuntimeIntelligence({
  enabled: import.meta.env.DEV && debugToggle === true,
  framework: 'lit',
});

const RuntimeBase = loaded.enabled
  ? loaded.frameworkModule.LitDebugMixin(LitElement)
  : LitElement;

customElements.define('my-app', class extends RuntimeBase {});
```

A static `LitDebugMixin` import is still valid when simpler wiring matters more than bundle isolation. R6.2 prevents adapter/collector activation while disabled, but static imports still ship code in the production bundle.

## Safe enablement recipes

### Vite

```js
const enabled = import.meta.env.DEV && localStorage.getItem('runtime-intelligence') === 'on';
```

### Webpack/application config

```js
const enabled = process.env.NODE_ENV !== 'production' && appDebugConfig.runtimeIntelligence === true;
```

### Controlled production investigation

If a consuming organization intentionally allows diagnostics in a production-like environment, gate it behind an application-owned authorization/feature flag and an explicit session toggle. Do not trust a bare query-string parameter by itself.

The loader only accepts literal `true`; truthy strings such as `'true'` do not activate it.

## Panel and reports

The canonical panel is optional and should be dynamically loaded only when needed.

It supports local/user-triggered JSON and HTML report export. Runtime Intelligence itself does not add an upload endpoint, beacon, analytics collector, or background telemetry transport.

Normalized report format: `runtime-intelligence-report/1`.

Recommended support workflow:

1. reproduce the issue;
2. refresh/open the panel;
3. inspect Intelligence/Opportunities and evidence level;
4. add a short reproduction note;
5. export JSON + HTML;
6. compare with a post-fix replay/baseline where applicable.

## Troubleshooting

### `ERR_PACKAGE_PATH_NOT_EXPORTED`

Do not import deep repository paths such as `runtime-intelligence/lit/src/...`. Use only documented package surfaces: `/loader`, `/core`, `/react`, `/lit`, `/panel`, `/panel/lit`.

### Works from repository, fails after install

Run:

```bash
npm run package:validate
npm run onboarding:validate
```

This usually indicates an export/packaging mismatch. R6.3 validation installs the packed tarball into a temporary consumer rather than importing directly from the source tree.

### React loads but no evidence appears

Check:

- the loader returned `enabled: true`;
- the application is wrapped by `RuntimeIntelligenceProvider`;
- the runtime passed to the provider is the same runtime whose `store` is passed to the panel;
- the provider remains mounted long enough for effects/profiler events to occur.

### Lit loads but component evidence is absent

For strict conditional loading, ensure the instrumented base class is chosen before `customElements.define()`. Existing classes cannot be retroactively changed to extend `LitDebugMixin` after registration.

### Panel is not visible

Verify `panel: true`, then mount it using `mountRuntimeIntelligencePanel({ store: runtime.store })`. Loading the panel module alone does not mount UI.

### Network interception appears to remain after teardown

R6.2 teardown restores host methods only if Runtime Intelligence still owns the installed wrapper. If another library patches `fetch`, XHR, or console after Runtime Intelligence, teardown intentionally does not overwrite that newer patch.

### Concern about sensitive runtime data

The shared evidence store uses the enterprise-safe privacy policy by default. Do not pass `privacyPolicy: false` outside an explicitly trusted/local diagnostic context.

## Reproducible onboarding validation

Run:

```bash
npm run onboarding:validate
```

The validator:

1. creates a real `.tgz` with `npm pack`;
2. creates an isolated temporary consumer package;
3. installs the tarball plus React/Lit peer/runtime prerequisites;
4. imports `/loader`, `/core`, `/react`, and `/lit` from the installed artifact;
5. proves the disabled loader contract;
6. proves React and Lit dynamic loader paths resolve from the packed install;
7. removes the temporary workspace.

This requires normal npm registry access for React/Lit dependency installation. It is a release/onboarding check, not a browser runtime test.

## Release validation checklist

Before calling an R6 build distributable:

```bash
npm run package:validate
npm run production:validate
npm run onboarding:validate
npm test
```

In addition, run one real browser smoke in the React Fault Lab or a consumer app whenever runtime/panel behavior changes.

## TrustWeave

No TrustWeave repin is required merely for onboarding documentation/validation. Keep the validated dogfood SHA until a later mission intentionally consumes an R6 productization baseline.
